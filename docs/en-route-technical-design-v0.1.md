En-Route Technical Design

Version: 0.1 Draft
Status: Working Design
Project: En-Route Healthcare Interoperability Framework

1. Purpose

En-Route is a healthcare interoperability and migration framework designed to move prioritized patient and clinical information between healthcare systems while preserving source identity, provenance, auditability, and clinical meaning.

The framework is intended to remain vendor-neutral.

FHIR R4 is the preferred internal representation and the default integration mechanism where the receiving system supports the required FHIR operations. Destination-specific delivery mechanisms such as CSV and HL7v2 are supported when operational or EHR constraints make them more appropriate.

The initial implementation uses synthetic FHIR data generated by Synthea and HAPI FHIR as a development target.

2. Design Principles
2.1 FHIR First, Not FHIR Only

FHIR R4 is En-Route's primary interoperability model.

Source
   ↓
FHIR / Source Adapter
   ↓
En-Route
   ↓
Validation
   ↓
Mapping / Transformation
   ↓
Destination Adapter
   ├── FHIR
   ├── CSV
   └── HL7v2

FHIR should be used when the destination supports an appropriate write workflow.

En-Route should not assume that because an EHR supports a FHIR resource for reading, it also supports creation, bulk loading, or migration of that resource.

2.2 Vendor Neutrality

En-Route must not become an Epic-specific migration utility.

Epic, Oracle Health, HAPI FHIR, and future destinations should be treated as target implementations with different capabilities.

Destination constraints are handled through adapters and configuration rather than changing En-Route's underlying clinical model.

2.3 Preserve Structured Data

When a destination cannot accept structured clinical information, En-Route should preserve the original structured representation internally.

For example, a medication PDF sent to Epic is a delivery artifact. It does not replace the structured MedicationRequest information retained by En-Route.

2.4 Human Clinical Authority

En-Route can classify, normalize, map, validate, and recommend routing.

It should not make clinical decisions that belong to clinicians or organizational governance.

Receiving-system reconciliation workflows should be used where available.

2.5 Configuration Over Hard Coding

Customer-specific requirements should be configurable where practical, including:

source system identifiers
output fields
output column names
destination adapter
terminology mappings
migration inclusion/exclusion rules
identifier systems
document types
reconciliation policies
3. MVP Scope

The MVP is deliberately limited to five clinical datasets.

Dataset	FHIR Resource	MVP
Patient	Patient	Yes
Allergy	AllergyIntolerance	Yes
Immunization	Immunization	Yes
Medication	MedicationRequest / Medication	Yes
Problem List	Condition	Yes

The MVP will not be expanded until these five datasets have functioning migration paths.

Deferred

The following are explicitly outside MVP scope:

Encounter
Appointment
Procedure
Observation
DiagnosticReport
DocumentReference beyond medication fallback
CarePlan
CareTeam
Claim
ExplanationOfBenefit

Likely post-MVP sequence:

Encounter → Appointment → Procedure

These resources can reuse much of the Patient, Practitioner, Organization, Location, and reference-resolution infrastructure.

4. Supporting Reference Resources

En-Route must resolve clinical-resource references to supporting resources such as:

Patient
Practitioner
Organization
Location

Reference resolution may include:

urn:uuid:...
Resource/id
Resource?identifier=...
absolute FHIR URL

Source-to-target identifiers should be maintained through crosswalks rather than replacing source identifiers.

5. File Processing Architecture

Although initial development uses individual Synthea files, En-Route is designed for batch processing.

Each source patient file is an independent unit of work.

incoming/
     ↓
processing/
     ↓
parse / validate
     ↓
extract / transform
     ↓
destination processing
     ↓
SUCCESS ──→ archive/

FAILURE ──→ failed/
5.1 File Claiming

A source file is moved from incoming to processing before processing begins.

This prevents multiple workers from independently processing the same source file.

5.2 Successful Processing

A file is archived only after the required processing step completes successfully.

5.3 Failure

Failed files are moved to a dedicated failure location and logged for investigation/reprocessing.

5.4 Duplicate Protection

SHA-256 hashes are used to identify previously processed source files.

This protects against duplicate processing even if the same file is later copied back into the incoming directory.

5.5 Concurrency

Initial processing uses one patient file at a time.

This is a correctness decision rather than an architectural limitation.

Future versions may run multiple workers:

Worker 1 → Patient A
Worker 2 → Patient B
Worker 3 → Patient C
Worker 4 → Patient D

Each worker continues to treat one patient file as its unit of work.

6. Processing State and Database

SQLite is used initially for lightweight transactional state.

Current responsibilities include:

processed-file ledger
SHA-256 tracking
processing status
error information
timestamps

Future responsibilities may include:

Patient crosswalk
Practitioner crosswalk
Organization crosswalk
Location crosswalk
Encounter crosswalk
migration run history
reconciliation status
exception queues

A future Azure deployment may replace SQLite with an appropriate managed relational database without changing the core migration model.

7. Patient Migration
7.1 Source

FHIR Patient

7.2 Epic-Oriented Delivery

The primary realistic conversion output is a configurable CSV/delimited file.

Example:

HospA Patient
      ↓
En-Route
      ↓
Patient migration CSV
      ↓
Destination HIM / conversion process
      ↓
Patient creation / matching / duplicate resolution

En-Route should not generate the authoritative destination Epic patient ID.

Patient matching, duplicate resolution, overlays, and final identity acceptance remain destination HIM/EMPI responsibilities.

HospA identifiers should be retained as source/external identifiers where permitted by destination policy.

7.3 Configurable CSV

En-Route maintains a richer internal Patient representation.

Customer configuration determines which fields are written to a particular output.

Example internal fields:

source_system
source_fhir_patient_id
source_mrn
mrn_system
family_name
given_name
middle_name
birth_date
gender
phone
address
marital_status
language
source_filename
source_sha256
processed_utc

A destination may request only:

SOURCE_MRN
LAST_NAME
FIRST_NAME
DOB
SEX
ZIP

Changing destination requirements should not require changes to Patient extraction code.

7.4 FHIR Patient Path

FHIR Patient creation will also be implemented against HAPI FHIR for:

FHIR API experience
standards testing
target-ID generation
crosswalk development
later clinical-resource testing
8. Crosswalk Architecture

Crosswalks are a core En-Route capability.

Example:

HospA Patient ID
       ↓
En-Route crosswalk
       ↓
Target Patient ID

Conceptual Patient crosswalk:

source_system
source_patient_id
source_mrn
target_system
target_patient_id
created_utc

The initial target will be HAPI FHIR.

Example:

HospA
a29acfed-...
       ↓
HAPI Patient/12345

Subsequent clinical records use this mapping:

HospA MedicationRequest
      ↓
source Patient reference
      ↓
Patient crosswalk
      ↓
target Patient/12345

Crosswalk ingestion should remain separate from Patient loading so that a HAPI-generated crosswalk can later be replaced by an Epic/HIM-generated crosswalk without rewriting clinical migration logic.

9. Allergy Migration
9.1 Source

FHIR AllergyIntolerance

9.2 Preferred Delivery

FHIR API.

HospA AllergyIntolerance
          ↓
En-Route
          ↓
validate / normalize
          ↓
Patient crosswalk
          ↓
FHIR AllergyIntolerance
          ↓
Destination

Epic publicly supports an AllergyIntolerance create workflow in which incoming information can enter an outside-data/reconciliation process rather than immediately becoming authoritative confirmed allergy information.

Oracle Health also supports AllergyIntolerance creation.

Therefore FHIR is the preferred En-Route route.

HL7 may remain a destination-specific adapter where required but is not the preferred MVP path.

9.3 Important Semantic Rule

Absence of AllergyIntolerance records does not mean:

No Known Allergies

An empty allergy dataset means allergy information is absent/not supplied unless the source explicitly represents NKDA.

En-Route must never infer NKDA from missing allergy data.

10. Immunization Migration
10.1 Source

FHIR Immunization

10.2 Preferred Delivery

FHIR remains the primary En-Route representation and should be used for destinations that support Immunization creation.

Examples include standards-compliant FHIR targets and Oracle Health-supported workflows.

FHIR Immunization
       ↓
En-Route
       ↓
FHIR POST / Immunization
10.3 HL7v2 Adapter

HL7v2 VXU is an alternate structured delivery mechanism.

FHIR Immunization
       ↓
En-Route
       ↓
FHIR → VXU transformation
       ↓
HL7v2 VXU
       ↓
Destination EHR

This is particularly relevant where an EHR/customer supports traditional immunization interfaces but does not expose the required FHIR create operation.

10.4 Bulk FHIR Clarification

FHIR API write support must not be confused with FHIR Bulk Data support.

En-Route may use:

individual FHIR POST operations
FHIR transaction/batch Bundles where explicitly supported

without claiming that the target supports FHIR bulk import.

FHIR Bulk Data $export functionality does not imply bulk-write capability.

11. Medication Migration

Medication is expected to require destination-specific behavior.

11.1 Source

Primary source resource:

MedicationRequest

Referenced Medication resources must be resolved where necessary.

En-Route must preserve the distinction between:

Medication.status

and:

MedicationRequest.status

A Medication resource being active does not mean the patient is actively taking that medication.

11.2 Status Preservation

Source status must be retained.

For example:

MedicationRequest.status = completed

must not automatically be converted to:

active

simply because a destination create API requires an active medication.

Migration policy determines whether a source medication qualifies as a current, historical, excluded, or review candidate.

11.3 Preferred Delivery

FHIR is the preferred En-Route medication delivery mechanism where the target supports an appropriate structured write workflow.

HospA MedicationRequest
          ↓
En-Route
          ↓
normalize / validate
          ↓
Patient crosswalk
          ↓
FHIR
          ↓
Destination
11.4 Epic Constraint

En-Route must not assume that Epic provides a generic MedicationRequest migration POST equivalent to a general-purpose FHIR server.

Epic supports external/outside medication concepts and specialized medication workflows, but its public write capabilities are more constrained than simply bulk creating native medications.

11.5 Epic/Customer Fallback

Where structured medication ingestion is unavailable or not accepted by the customer, En-Route will support an MVP fallback:

Structured Medication Data
          ↓
En-Route
          ↓
Human-readable PDF
          ↓
Embedded in HL7v2 MDM
          ↓
Interface
          ↓
Epic document
"Outside Medications - Hospital A"

The PDF is a delivery artifact only.

The original structured medication data remains available for auditability and future processing.

11.6 Deferred Medication Delivery

A future option may support:

HL7 MDM
   +
link/reference to externally stored PDF

This is explicitly deferred and is not part of MVP.

11.7 Possible Post-MVP Transitional Service

En-Route may eventually support just-in-time retrieval of external medication information during a destination clinical workflow.

Conceptually:

HospA medication data
        ↓
En-Route transitional repository
        ↓
Upcoming appointment / pre-chart / chart workflow
        ↓
Destination-supported trigger
        ↓
En-Route
        ↓
External medication context
        ↓
Clinician review/reconciliation

This must not be interpreted as permission to silently populate a destination's authoritative active medication list.

The exact workflow would depend on supported EHR integration mechanisms such as CDS Hooks, SMART workflows, outside-data workflows, or customer-specific interfaces.

This feature is post-MVP.

12. Problem List Migration
12.1 Source

FHIR Condition

However:

FHIR Condition ≠ automatically a Problem List item

The source Condition must first be classified.

12.2 Classification Problem

Source Conditions may represent:

active clinical problems
encounter diagnoses
historical conditions
pregnancy/history
social determinants of health
social history
workflow situations
other contextual information

Therefore En-Route cannot blindly migrate every Condition to the destination Problem List.

12.3 Initial Classification Strategy

Deterministic terminology and policy rules are preferred before AI.

Conceptual process:

Condition
    ↓
FHIR category/status
    +
SNOMED concept
    ↓
terminology hierarchy / value sets
    ↓
organization migration rules
    ↓
classification

Possible classifications:

problem_list
sdoh
history
exclude
review
12.4 SNOMED

SNOMED CT is not an SDOH-only or clinical-only coding system.

It can represent:

disorders
findings
social concepts
situations
contextual information
procedures
other healthcare concepts

Therefore:

has SNOMED code → clinical Problem List

is an invalid rule.

Likewise, semantic labels such as (finding) are insufficient by themselves.

For example, both a medical finding and an employment-related social finding may be represented as SNOMED findings.

12.5 AI

AI is not required for the primary MVP classification engine.

AI may later assist with:

ambiguous legacy codes
unstructured descriptions
uncertain mappings
exception prioritization

but should not autonomously determine authoritative clinical migration semantics.

12.6 Destination Delivery

FHIR Condition is the preferred delivery method where supported.

Epic publicly supports a Condition Create workflow for problems that can enter an outside-data/reconciliation process.

This provides an important safety boundary:

En-Route
"This appears to be a Problem List candidate"
             ↓
FHIR Condition
             ↓
Epic reconciliation workflow
             ↓
Clinician
             ↓
accept / modify / reject
             ↓
authoritative Problem List

En-Route therefore needs high-quality, explainable candidate classification rather than pretending to replace clinical review.

13. Destination Adapter Strategy

En-Route should separate clinical transformation from destination transport.

                    ┌── FHIR Adapter
                    │
FHIR → En-Route ────┼── CSV Adapter
                    │
                    ├── HL7 VXU Adapter
                    │
                    └── HL7 MDM/PDF Adapter

Adding a new destination mechanism should not require rewriting clinical extraction.

14. Current MVP Delivery Matrix
Dataset	Preferred En-Route Route	Alternate / Destination-Specific Route
Patient	FHIR + configurable canonical processing	CSV for Epic-style conversion
Allergy	FHIR AllergyIntolerance	HL7/customer-specific if required
Immunization	FHIR Immunization	HL7v2 VXU
Medication	FHIR MedicationRequest	HL7v2 MDM + embedded PDF
Problem List	FHIR Condition	HL7/customer-specific if required

This matrix represents En-Route design intent, not a guarantee that every EHR/customer configuration supports every operation.

15. Auditability and Provenance

Every migration operation should eventually be traceable.

Useful audit information includes:

migration run ID
source system
source patient identifier
source resource identifier
source filename
source SHA-256
source resource type
target system
target resource identifier
processing timestamp
transformation performed
migration status
validation result
error/exception reason

FHIR Provenance should be evaluated where supported.

Source identifiers should not be discarded simply because a destination identifier has been assigned.

16. Error and Exception Handling

Records should not disappear because they cannot be automatically classified or loaded.

Conceptual outcomes:

SUCCESS
FAILED
REVIEW_REQUIRED
EXCLUDED_BY_POLICY
DUPLICATE

Ambiguous clinical information should be routed to an exception/review process rather than guessed.

17. Security and PHI

Initial development uses synthetic Synthea data.

Production use would require additional controls including:

authentication/authorization
encryption in transit
encryption at rest
secrets management
least-privilege service access
PHI-safe logging
retention policies
audit logging
customer security requirements

Production PHI should never be written indiscriminately to application logs.

Detailed production security architecture is deferred until the core migration workflow is established.

18. Cloud Direction

Development is local-first.

Current:

22. Guiding Principle

En-Route should answer three separate questions in order:

1. What does the source data mean?
             ↓
2. What should be migrated?
             ↓
3. How can this destination safely receive it?

Transport should not determine clinical meaning.

Destination limitations should not destroy source structure.

And automation should not replace clinical governance where clinical judgment is required.
